# 为什么 Agent 评测不能只看回答质量

## 问题

很多大模型评测仍从“回答得像不像标准答案”开始：事实是否正确、表达是否完整、格式是否符合要求。这些维度对聊天产品很重要，但当产品从回答问题走向执行任务，它们已经不足以代表成功。

用户要求生成一份 Word 报告，真正关心的不是对话框里那段总结是否漂亮，而是文件有没有生成、能不能打开、内容是否齐全。用户要求制作可筛选的网页，HTML 文件存在也不等于按钮真的可用。只评文本，会把大量“看起来完成”的失败判成成功。

## 真实现象

在 [Agent 评测实验室](https://github.com/ljj24681379-png/agent-evaluation-lab) 中，我把任务完成拆到整条交付链路：任务理解、工具调用、文件产物、自动校验、失败修复和最终交付。同一任务还会重复运行，因为一次成功并不代表用户下一次还能得到相同结果。

一个典型情况是三次运行结果为“成功、失败、成功”。单次平均成功率看上去尚可，但用户感受到的是每三次就可能失败一次。对任务型产品而言，这种波动会直接降低信任。因此“三次全成功率”比单次成功率更严格，也更接近稳定交付的产品目标。

## 为什么会发生

Agent 的结果不只由模型生成能力决定。模型可能理解正确，却传错工具参数；工具可能返回成功，生成器却输出损坏文件；文件可以打开，交互功能却失效；第一次修复还可能改错位置。任何一个节点失败，用户拿到的都不是有效成果。

另一个原因是评测目标容易被指标牵着走。如果只定义“答案相似度”，团队自然会优化 Prompt 文案；如果把工具失败与产物失败分开，问题才会被路由到 Tool Schema、Validator 或 Product Flow。好的分类不是为了报表更丰富，而是为了知道下一步改哪里。

## 方法

我更倾向用四层结构设计 Agent 评测：第一层看任务是否被正确理解，特别是交付物是否识别完整；第二层看工具是否按预期调用，错误能否中断；第三层对文件和交互做程序化校验；第四层重复运行并观察稳定性、修复能力和时延长尾。

通过后仍需要抽检。程序擅长判断文件能否打开、字段是否存在，模型复核适合检查语义覆盖，人工则用于审查重要任务和边界案例。三者不是互相替代，而是分别承担确定性检查、语义判断与责任确认。

## 产品判断

Agent 评测的对象不应该是“最后一句话”，而应该是“从需求到成果的完整交付”。这会改变产品优先级：模型选择不再只比较谁答得最好，而要判断什么场景需要更稳的工具调用、什么任务必须强制校验、什么失败应该转人工。

评测的最终产物也不应只是排行榜。它应该进入模型路由、执行策略、超时机制和发布门槛。只有当失败被转成产品动作，评测才真正参与了产品建设。
