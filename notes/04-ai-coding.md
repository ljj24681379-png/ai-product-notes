# AI Coding 真正改变的不是写代码速度

## 问题

谈到 AI Coding，最常见的衡量方式是“代码写得更快了多少”。对产品经理而言，这个视角太窄。真正重要的变化不是产品经理替代工程师，而是很多原本停留在文档、口头说明和静态原型里的判断，可以更早变成可运行、可测试、可被质疑的东西。

## 真实现象

一份 PRD 可以写清按钮、页面和流程，但团队仍可能对“用户如何理解”“异常如何出现”“等待时应该看到什么”有不同想象。静态设计稿能表达视觉，却难以验证任务回放、状态切换和真实内容密度。直到开发完成，这些分歧才集中暴露，修改成本已经变高。

在个人项目中，我会用 AI Coding 把产品判断直接推进到轻量 Demo。例如在 Agent 评测项目里，任务回放不是一个抽象模块，而是可以点击的步骤与状态；在上下文工程项目里，用户能看到 AI 为什么继续查、证据如何支持结论。交互一旦真实存在，评审就会从“概念是否好听”转向“用户是否看得懂”。

## 为什么会发生

传统协作把产品意图经过 PRD、设计、技术理解再转成软件，每次交接都会损失细节。AI Coding 降低了实现最小闭环的成本，让产品经理能提前承担更多验证工作。但如果只追求生成代码数量，也会得到另一种低效：页面很多、判断很少，边界和数据都经不起检查。

代码本身不是作品的核心。核心是它是否让关键假设变得可观察：用户会不会点击、信息是否过载、失败是否可理解、规则能否执行、验收是否明确。

## 方法

我倾向先写“要验证的判断”，再让 AI 参与实现。一个 Demo 只承载一到两个关键问题，例如“执行轨迹能否增加信任”或“普通模式与可靠模式的差异是否一眼可见”。数据边界、核心状态和验收标准要由人明确，AI 负责加速结构搭建、样式实现、测试脚本和重复修改。

生成后还需要像对待真实需求一样验收：移动端是否错位，按钮是否可用，文案是否夸大，数据是否自洽，仓库能否由别人独立理解。AI 可以写测试，但最终的产品判断不能外包给测试通过率。

## 产品判断

AI Coding 对产品经理最大的影响，是缩短“想法—原型—反馈—修正”的循环，并让产品责任向交付侧延伸。它不会取消专业分工，也不意味着产品经理需要成为全栈工程师。

更准确地说，产品经理获得了一种新的表达媒介：除了文档和设计稿，还能用可运行系统说明需求、展示边界、沉淀验收。速度只是表象，真正的变化是产品判断可以更早接受现实检验。
